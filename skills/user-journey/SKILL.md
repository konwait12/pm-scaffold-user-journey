# 用户旅程

## 作用与边界

这个 skill 描述角色为了完成业务目标，实际经历了哪些生命周期阶段、行为、触点、分支、阻碍和结果。它产出：

- `user-journey.md`：人和 AI 都能直接阅读的旅程基线候选；

- `user-journey.governance.md`：来源、知识状态、澄清、审计和主文档哈希；

- 按需的 `user-journey.board.html`：用于人审的单文件可交互旅程审阅板，不是页面原型。

不写用户故事卡片、范围基线、功能清单、页面、字段、接口、业务规则、状态机或验收标准。出现这些内容时，保留到角色行为和业务结果层，并路由到下游 skill。

## 输入边界

优先输入是已确认的 `project-background-goal` 产物，以及 PM 在本次任务提供的原始旅程材料（会议、PPT、PDF、图片、口述、邮件、流程草图或现状说明）。只能使用本次任务中的这些材料和 PM 的明确回复。

### 项目专属基线（可选）

如果本次工作有"项目专属基线材料"（例如飞书/钉钉/Notion 上的项目章程文档、决策记录、既有 PRD 等），可以在启动时由 PM 指定基线来源，执行 skill 前先实际读取原文，再区分基线明确决定、讨论/建议和 AI 解读。基线原文是来源，AI 摘要不是来源；不能用其他项目经验、通用用户旅程案例或模型记忆替代基线材料。基线原文与上游 `project-background-goal` 共同规定本 skill 的独立使用、人读纯净、原始材料测试和治理外置边界。

示例（飞书 CLI）：

```bash
lark-cli docs +fetch \
  --doc <PM-指定的-doc-id> \
  --doc-format markdown \
  --scope full \
  --format pretty
```

以命令返回的完整原文为准，并在治理伴随文件记录检索命令、文档 ID、检索日期和使用的章节/时间点。若 CLI 不可用、文档无法读取或只返回摘要，先停止在 `needs_user_input`，请 PM 提供原文或修复访问；不得用本文件、交接文档或模型记忆代替。

先把基线原文拆成四类记录：基线明确决定、基线中的业务示例、基线讨论/建议、AI 解读。只有第一类可以直接约束本 skill；第二类只有在 PM 本轮明确指定时才可作为旅程事实；第三、四类只能作为方法线索，不能写进项目旅程。

基线明确的工作协议是：先与 AI 说清楚业务本质、旅程起点和终点、主题/框架，再逐步完善场景；不要把第一次输出当成最终答案；每个 skill 都有独立输入和输出，可以单点验证，也可以把阶段性产物交给下一环节；用具体原始材料跑 skill，并拿人工期望或独立参照比对结果。用户旅程必须从角色和业务结果出发，不能从页面或功能清单出发。

不得用联网搜索、通用行业知识、模型记忆、其他项目文件、既有 PRD、历史案例、旧测试夹具或 reference 示例补充项目事实。对材料没有提及的内容，不得写成"不存在"；只能标为未知并提问。

基线里的业务示例不是默认测试数据。除非 PM 明确指定其原文、范围和测试目的，否则不得把这些示例带入当前旅程、问题选项、HTML 或验证结论。

当 PM 要求测试 AI 对原始材料的理解时，启用"材料隔离测试模式"：只把本轮明确指定的原始文件和 PM 在本轮给出的说明作为事实输入；已确认的上游产物、其他需求实例、旧产物、reference、搜索结果和模型记忆都只能作为方法背景，不能补充、纠正或暗示测试答案。测试产物中的每条事实必须能回到指定原始材料的位置。

若本文件与通用参考文档的调研或示例规则冲突，以本节输入边界为准；未获 PM 明确授权时，不联网、不调用外部资料来填补旅程事实。

上游背景目标未达到 `confirmed` 时，不要假装已经有旅程基线：如果本次已有原始旅程材料，可以基于材料生成候选旅程，但必须把上游内容标为候选/待确认，不能写成已确认事实；如果角色、生命周期或目标不足，输出预检回执和澄清问题，状态保持 `needs_user_input`。只有授权人类确认后，才可把它作为下游基线。

## 使用协议（来自 2026-08-27 会议约定）

按会议原文的执行协议，本 skill 必须遵守以下三条：

1. **渐进式产出** — 不假设一次对话就能得到最终旅程图。按 8 步循环**逐步推进**：先与 AI 谈清业务本质、旅程起点和终点、主题/框架，再完善场景；不要先把产物当最终答案。
2. **单点验证** — 本 skill 拥有清楚独立的输入和输出；**可以单独运行并验证**，不依赖 pipeline、registry、下游产物或其他 skill。验证时只用 PM 指定的原始材料，并与 PM 人工期望或独立参照对比。
3. **用具体案例反复跑** — 拿一个真实业务案例跑本 skill，看产物是否清晰；如果不符合预期，**调整 skill 再跑**，直到产物能直接说清楚"角色 × 阶段 × 行为 × 触点 × 痛点 × 机会"。这是会议原文强调的迭代闭环。

## 对话流程

### 1. Preflight：确认输入是否足够

从上游和本次材料提取：

- 每个角色要完成的生命周期目标；

- 已明确的阶段、触发事件、行为和触点；

- 已明确的正常、备选、异常、失败、交接和恢复路径；

- 能观察到的情绪线索或痛点证据。

评估成熟度：

- `L0`：没有角色或目标；

- `L1`：只有一个角色或一个阶段线索；

- `L2`：有多个角色但阶段/触点不完整；

- `L3`：角色、阶段、触点和部分分支清楚；

- `L4`：上游已确认且旅程材料充分。

先给 PM 一段材料解读，区分“材料明确说了什么”“AI 对高层行为链的理解”“材料无法证明什么”。先确认旅程要完成的业务事件、起点和终点；若起点或终点不清楚，先给出 A/B/C 三选一澄清，不要先画一条完整的理想路径。本步输出作为 §3.5 粒度决策的输入材料，但粒度本身在 Intake 之后才正式决定。

### 2. Intake：按角色还原实际行为

对每个角色单独记录：目标、触发、可观察动作、触点、决策点、交接、异常退出、恢复动作和情绪证据。材料若只给功能或页面，改写为角色行为；例如“进入列表页”应还原为“查找自己的产品记录”。

保留来源位置和原意。禁止把“系统展示了某页面”自动写成用户痛点，也禁止把“方案列了某功能”自动写成业务目标。

### 3. Think：使用必要透镜

至少应用并记录会改变候选产物的发现：

- 第一性原理：角色真正要完成的业务结果是什么？去掉方案名称后问题还成立吗？

- 系统思维：哪些触点跨角色、系统、渠道或外部依赖？哪些现有环节不能破坏？

- 同理心/角色视角：角色在每个阶段要承担什么成本，哪些可观察行为表明卡住或不确定？没有证据就标未知。

- 对抗性审视：是否存在一个合理的替代路径、反例或失败前提，使当前旅程不成立？

- 逆向验证：要获得目标结果，哪些阶段和交接不可缺？成功前提是否有负责人？

- 知识边界：事实、决定、假设、AI 推断、未知、冲突分开保存。

不要把完整思考过程倾倒到主文档；只把会影响旅程结构、路径覆盖或澄清的问题写入产物。

### 3.5 粒度决策：先选业务层还是产品层，再动笔

会议（2026-08-27）明确把 user journey 拆成两段粒度，必须在 Intake 之后、Generate 之前先决定。不能在模糊状态下"先画一条完整的理想路径"。

#### 两段粒度的边界

| 维度      | 业务层（business-level journey）              | 产品层（product-level / UX journey）                 |
| ------- | ---------------------------------------- | ----------------------------------------------- |
| 起点 / 终点 | 一个具体业务事件的生命周期（例如：DP 创建前 → 创建过程中 → 创建完成后） | 完成该业务事件的系统交互步骤（例如：客人收到短信 → 点链接 → 进入过渡页 → 落到小程序） |
| 阶段粒度    | 3–6 段高层阶段，每段对应一个完整业务子事件                  | 每个业务阶段可下钻为多步 UI 步骤；同阶段的不同路径（如短信进入 vs 邮件进入）需并列   |
| 行为描述    | 角色在该业务事件中的目标、触发、决策、交接                    | 角色在具体界面/通道中的动作、跳转、反馈、异常处理                       |
| 触点      | 业务级别的入口与通知（短信 / 邮件 / 服务号 / DP）           | 页面 / 弹窗 / 浏览器过渡页 / 小程序启动动画 / 标签 / 红点            |
| 不应出现的产物 | 页面名称、字段、接口、跳转 URL                        | 用户故事卡（"作为…我希望…"）、功能清单、验收标准                      |

#### 决策顺序（强制）

1. AI 先给出粒度判断 + 证据（引自会议原文或 PM 原始材料）。
2. 在 Clarify 阶段第一个澄清问题必须是粒度（`Q-GR-001`），给出 A/B/C 选项：

   - A. 只做业务层：画清生命周期阶段、角色行为、交接和异常。

   - B. 只做产品层：把已知业务事件直接展开为 UI 步骤与跳转（前提是业务层已在前置产物确认）。

   - C. 都要：业务层为主，产品层作为"业务阶段 X 的展开"附在每个阶段之后。
3. 若 PM 选择 B 但上游业务层尚未确认，必须先停在 `needs_user_input`，让 PM 选择"先补业务层"或"用 AI 推断的业务层先展开产品层（标 AI\_INFERENCE）"。
4. 主文档 frontmatter `granularity` 字段必须记录：`business` / `product` / `business+product`。

#### 何时回退到上游

- 业务层旅程的阶段划分不明确（缺起点或终点）→ 回到 §1 Preflight，要求 PM 给出起点事件和终点事件。

- 产品层旅程找不到对应的业务阶段 → 回到业务层补全，再展开。

- AI 写出"点击某按钮""进入某页面"且粒度声明是 `business` → 校验器视为 `uj.granularity_leak` 警告，必须改为业务事件表述。

#### 与下游 skill 的边界

- 业务层 → 可直接喂给 `user-stories`、`feature-list`、`functional-flow`。

- 产品层 → 可喂给 `page-design`、`interaction-rules`、`exception-handling`；不替它们生成页面或规则。

- 同一份主文档若同时含两种粒度，必须在 `角色旅程矩阵` 用子表分开。

### 4. Clarify：AI 判断后提问

每轮最多 5 个高影响问题；优先处理会改变角色、阶段、路径、触点、情绪判断或下游使用的问题。每个阻断问题都要给：AI 初步判断、材料证据、三个互斥选项（A/B/C，可加“其他”自由回答）、影响、负责人和是否阻断。

澄清按会议要求渐进推进：先问业务目标、起点/终点和角色责任，再问主路径、分支、异常和交接，最后才讨论可能的实现方案。AI 可以列出通知或触达等可行选项供 PM 选择，但不能擅自把某个选项写成已决定的业务需求。

遇到以下情况必须停在 `needs_user_input`：角色责任冲突、主路径与备选路径无法判定、痛点/情绪只有 AI 猜测、交接归属不明、或旅程范围会随答案改变。不要通过行业常识“补齐”答案。

### 5. Generate：生成两份文档，HTML 按需

主文档 `user-journey.md` 使用技能自带模板（本 skill 目录内 `templates/user-journey.md` 的标题，治理文件用 `templates/user-journey.governance.md`），至少包括：一句话旅程叙事、业务生命周期分解、角色旅程矩阵、路径与情绪、触点/痛点/机会、覆盖与边界、待确认与风险、参考资料。

每个角色至少有一条独立叙事；每个已确认阶段说明触发、行为、触点、结果和路径类型。痛点必须来自材料或明确标为 AI 推断/未知；机会写成可观察的改进结果，不写成按钮、页面或接口。

状态只能是 `draft`、`needs_user_input`、`conditional_review` 或 `ready_for_human_review`，AI 永远不能写 `confirmed`。

当多角色多阶段需要现场审阅，或 PM 明确要求可视化时，生成 `assets/user-journey-board.html`：单文件、零外部网络依赖、按角色/阶段/路径筛选并可展开证据和未知项。它只呈现旅程材料，不新增页面、文案、功能或状态；具体契约见 `references/html-journey-board.md`。

可视化输出分两层，均只呈现旅程材料、不新增或改写内容，节点/阶段/角色须与 Markdown 主文档一致。HTML 画板全部为技能自带模板（本 skill 目录内 `assets/` 下），执行时复制模板、替换数据块即可，无需外部依赖：

**第一层（默认 · MD 内嵌）**：旅程主文档内的 Mermaid 代码块，覆盖全部常用图型（旅程、流程、泳道、时序、状态、甘特等），作为随文档版本管理的初版图，零额外文件。需要交互浏览时可选生成 `assets/journey-diagram-studio.html`：基于本地打包的 Mermaid（`assets/lib/mermaid.min.js`，离线可用），标签页切换 11 种图类型，左编辑源码右即时渲染。

**第二层（PM 汇报 · HTML 原生）**：当用户或 PM 要求"好看的图 / 汇报版 / 专门 HTML 版"时，生成 `assets/journey-map-studio.html`：纯 HTML/SVG 手绘（不依赖 Mermaid），三个视图 —— 旅程地图（角色切换：综合视角 + 每个角色一条独立旅程，含角色目标、路径类型推导的顺畅度曲线并标注 AI\_INFERENCE）、泳道流程图（角色泳道 + 正交连线，异常/失败/返工路径分色）、状态流（状态迁移 + 回路）。数据块与主文档角色旅程矩阵同源，替换 `DATA` 即可复用。

**第三层（PM 汇报 · 总览+流程图 v1.6）**：当 PM 想要"像 PRD 流程图那样、一整条旅程一图看完"时，生成 `assets/user-journey-flow.html`：**双视图**——① 总览图（默认）：横向 6 阶段泳道，全部角色 × 全部节点按阶段一列排开、主路径高亮、异常/失败/交接/恢复分色左边框，一张图看完整条旅程；② 节点详情：分阶段节点卡片（起点胶囊 / 终点胶囊 / 菱形决策节点），点击任意节点弹出详情（行为/触点/结果/证据）。支持角色 Tab 切换、阶段/路径/状态筛选、搜索、URL 参数直达（`?view=overview|flow`）。数据块在 `JOURNEY`（meta/stages/roles/nodes），替换即可复用；nodes 字段：id/role/stage/path/status/type/title/desc/behavior/touchpoint/result/evidence。type 可选 start/end/decision/exception/failure/handoff/recovery/alternative。总览图与节点详情两个视图都必须覆盖主文档全部角色 × 全部节点。

**节点覆盖率硬约束（三层可视化均适用）**：任何可视化产物必须覆盖主文档角色旅程矩阵中的**全部角色 × 全部节点，一个不缺**。`assets/journey-map-studio.html` 模板的 `DATA` 有三处节点载体（`roles[].nodes`、`swim.nodes`、`states`），最低覆盖标准：`roles[].nodes` 与 `swim.nodes` 两处都必须与主文档矩阵逐节点相等，`states` 仅在有状态迁移材料时填充。`assets/user-journey-flow.html` 模板的 `JOURNEY.nodes` 必须与主文档矩阵逐节点相等。生成前先数主文档节点总数，再数可视化数据块节点总数，两者相等才允许交付；缺节点 = 交付失败。角色视图不得把多角色旅程压缩成一条混合旅程——每个角色必须能独立查看，角色没有节点的阶段如实留空，不得虚构行为填充。主文档没有的信息（如逐角色情绪分值）用可解释的推导（如按路径类型推导顺畅度：normal/alternative=3、handoff/exception/recovery=2、failure=1）并显式标注 AI\_INFERENCE，禁止无证据编造。

**品类 / 变体分列规则（v1.2 · 源自盲测 A 类盲区）**：当材料对同一旅程按品类、用户类型、渠道或设备分列描述（如手袋 HBG 与成衣 RTW 的字段/入口/通知差异、All users 与 InCHANEL client 的页面差异），旅程矩阵必须分列节点或在节点内显式标注差异，禁止合并成笼统表述。材料分栏存在即视为差异线索；差异内容材料未给时标 UNKNOWN，不得默认两品类行为一致。

**触点 / 通知形态枚举清单（v1.2 · 源自盲测 A 类盲区）**：材料（尤其流程图、线框图）中出现的每一种通知与提醒形态都必须单独提取为触点，逐项核对：短信 SMS、邮件 EDM、服务号消息、小程序内提醒、红点、New 标签、弹窗提醒（reminder dialog）、二维码扫码、浏览器过渡页等。流程图里的独立图形节点（如 "Receive a reminder" 弹窗）不得窄化合并进相邻节点；材料给出的每个通知模版（如不同品类 EDM 版式）都要在触点或产品层展开中体现。

**矩阵空格语义（v1.2）**：角色 × 阶段网格中某角色在某阶段无节点时，必须显式写「—（未参与：<原因>）」，禁止留白——留白无法与漏填区分，覆盖审计会歧义。

**默认多角色泳道（v1.3 · 源自原材料共性分析）**：B2B2C 或服务类项目默认至少两条泳道，复杂项目加系统/后台泳道：

- **终端用户泳道**（C 端 / 客户）：用户感知到的旅程

- **一线执行者泳道**（FA / 店员 / 客服 / 运营）：为用户提供服务的后台操作

- **系统/后台泳道**（自动化处理 / 定时任务）：背后的系统自动化流程，可选

理由：几乎所有 B2B2C / 服务类项目，用户体验都依赖一线人员的操作质量；单角色（仅终端用户）的旅程图在这类项目中是不完整的。

**六阶段生命周期默认模板（v1.3）**：阶段命名建议先套模板，再根据项目特性调整。六阶段模板适用于大多数用户创建/管理数字资产/服务的项目：

- **S1 触发 / 创建**：旅程被触发，DP / 订单 / 记录被创建

- **S2 通知 / 触达**：通过多通道通知用户，告知旅程开始

- **S3 首次进入 / 激活**：用户从各种入口首次进入系统页面

- **S4 核心使用 / 查看**：用户浏览和使用核心功能

- **S5 管理 / 深度操作**：用户对资产进行管理操作（分享 / 删除 / 修改）

- **S6 退出 / 解绑 / 流失**：旅程结束，资产与用户解除绑定

**触达通道矩阵子模板（v1.3）**：用户旅程中的"触达/通知"环节，默认不是一个简单节点，需要展开为多通道矩阵，每个通道检查：

- 触发条件：什么时候发（实时 / 批次 / 定时）

- 发送时机：哪个阶段发

- 内容模板：标题 / 正文 / CTA 的差异

- 用户分层：身份 × 登录状态的分支走向

- 失败兜底：发不出去怎么办、用户收不到怎么走

每个通道都需要单独提取为触点，不能把"收到通知"合并成一个节点。流程图中每个独立通知图形节点都必须单独提取。

**分支完整性自检清单（v1.3）**：每个旅程节点完成后，必须自检是否覆盖了以下分支（材料没有时标 UNKNOWN，不能省略）：

- [ ] 是否区分了用户身份/等级？（All users / InCHANEL client 等）

- [ ] 是否区分了登录状态？（已登录 / 未登录）

- [ ] 新用户 vs 老用户的路径是否不同？

- [ ] 有权限 vs 无权限的处理是否完整？

- [ ] 空状态（无数据）是否有兜底？

- [ ] 数据异常/缺失是否有处理？

**异常路径触发点清单（v1.3）**：提供一份高频异常触发点清单作为审计自检，异常路径不能只靠分析师自由发挥：

| 层级      | 高频异常类型                   | 示例                 |
| ------- | ------------------------ | ------------------ |
| **入口层** | 无权限 / 非目标用户 / 链接失效       | SMS/EDM 链接被非目标用户访问 |
| **数据层** | 空数据 / 数据缺失 / 加载失败 / 部分失败 | DP 信息缺失按创建失败处理     |
| **操作层** | 创建失败 / 删除失败 / 网络异常       | 创建 DP 接口返回失败       |
| **权限层** | 登录过期 / 权限变更 / 多端冲突       | 会话过期需要重新登录         |
| **内容层** | 图片加载失败 / 内容过期            | DP 图片资源缺失不展示图片     |

这份清单必须在 Audit 阶段逐项检查，确保每个可能出异常的位置都有处理路径。

**服务能力映射层（v1.3）**：用户旅程不能只画前端用户看到的流程，应该增加一层"背后的服务能力映射"作为补充视图（或泳道）：

- 每个用户操作背后需要哪些后端服务能力

- 哪些依赖外部系统 / 第三方 API

- 外部依赖失败时的降级策略

- 数据来源是什么（实时 / 缓存 / 离线）

这项补充能帮助下游功能设计直接映射到后端能力，避免需求遗漏跨系统依赖。

**数据溯源表（v1.3）**：在旅程详细节点中增加数据维度，确保每个展示信息都能追溯来源：

| 字段  | 描述         | 来源服务     | 是否依赖外部 | 备注      |
| --- | ---------- | -------- | ------ | ------- |
| 字段名 | 展示给用户的信息字段 | 来源服务 API | 是/否    | 不确定/待确认 |

特别标注跨系统 / 跨团队的数据依赖，标记"不确定 / 待确认"的数据项。这项源自 BRD 实践，每个功能模块都有 Data source Specification 表。

### 6. Audit：重新阅读并反证

检查：

- 每个已确认角色和已确认阶段都有覆盖；

- 主路径、备选路径、异常/失败、交接/恢复的缺口显式列出；

- 情绪来自可观察证据，缺证据不编造"满意/焦虑/惊喜"；

- 每个痛点都能追到来源或 AI 推断，每个机会都能追到痛点；

- 行为层没有泄漏成页面、功能或技术实现；

- 目标、前提、依赖和未知能被下游读取；

- HTML 与 Markdown 的角色、阶段、路径和状态一致。

- 本次验证是否只使用了 PM 指定的原始材料；没有把会议示例、旧产物或参考文档泄漏为答案。

- **v1.3 Audit 新增项**：

  - 是否应用了分支完整性自检清单？（若无材料分支，是否标了 UNKNOWN？）

  - 异常路径触发点清单是否逐项检查？（入口/数据/操作/权限/内容五层）

  - 若为 B2B2C 项目，是否设置了至少两条泳道（终端用户 + 一线执行者）？

  - 若涉及多通道触达，是否展开了通道矩阵（触发条件/发送时机/内容模板/用户分层/失败兜底）？

  - 判断是否存在分类器泄漏：产物是否把"品牌理念"、"业务痛点"当成默认的背景标准，而不是从材料实际提取？

运行 `scripts/validate_artifact.py <user-journey.md> --json`。修复阻断错误，并把非阻断未知写入治理文件。

### 7. Human Gate 与回流

向 PM 展示旅程摘要、角色与阶段覆盖、路径/情绪缺口、证据、待确认问题、HTML 审阅板（如有）和 Audit 结果。只有授权业务/产品负责人可以批准；机器校验不能确认。

已确认内容发生改变时，记录变更和下游影响，重新生成 Markdown/HTML、重跑 Audit，再回到人工评审。不要在下游 skill 中静默修补上游旅程。

## 完成标准

`user-journey.md` 与治理伴随文件同目录、同 artifact\_id 和版本；主文档可独立阅读且不包含机器治理表；治理文件记录所有重要来源、知识状态、澄清、Audit 和哈希；所有角色旅程、阶段、路径和未知均可追溯；可选 HTML 审阅板无外部依赖且只呈现已确认或明确标记的旅程信息；状态等待授权人类确认。
